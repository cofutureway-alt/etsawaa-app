## 4) RLS

**74/74 جدول فيه `ENABLE ROW LEVEL SECURITY`.** 64 بسياسة صريحة، و10 جداول staging بسياسة عبر حلقة `DO` (`*_admin_read` + `is_admin()`).

`FORCE ROW LEVEL SECURITY` على: `wallet_transactions`, `audit_logs`, `email_logs`.

| الدور | الوصول |
|---|---|
| زائر | `v_storefront_*` views، أقسام/ماركات/وسوم نشطة، attribute defs/options، governorates/areas، banners/pages، مراجعات منشورة، منتجات عبر `product_is_public(id)`، bucket `media`، دوال البحث والكوبون، INSERT على `contact_messages` |
| عميل | صفوفه في `profiles`, `user_addresses`, `cart_items`, `wishlist_items`, `recently_viewed`, `notifications`, `orders` (`user_id = auth.uid()`), `refund_requests`, `order_documents`, `reviews` |
| بائع | كل شيء عبر `own_vendor_id()` = `vendors.owner_id`؛ **لا SELECT على `orders`** — فقط RPC snapshots |
| staff | فقط مسارات `has_permission(...)`: `profiles` (`users.read`), `settings` (`settings.read/write`), `fn_admin_review_product` (`products.review`) |
| أدمن | `is_admin()` على كل جدول وكل RPC |

**ملاحظة:** لا توجد سياسة كتابة خارج صفوف المستخدم نفسه. كل كتابات التجارة/الدفتر تمر عبر RPC DEFINER، وجداول `orders` للقراءة فقط.

## 5) المال والمحفظة

- `fn_post_transaction` هو الكاتب الوحيد للدفتر، idempotent على `(vendor, type, ref)`.
- trigger `wallet_tx_apply` بعد INSERT: `earning` → pending، وكل نوع آخر → available.
- `fn_release_earnings`: pending → available بعد `hold_days`، يكتب `admin_adjustment 'release:<id>'` ويُنقص pending.
- `fn_post_pickup_fee`: `Σ qty × area.pickup_fee_piastres`، يُنشر مرة واحدة عند أول `handed_to_carrier`.
- `shipping_revenue` يُضاف **فقط** عند موافقة الأدمن على شحن البائع.
- الرصيد يمكن أن يصبح سالباً — بالتصميم، بلا قيد CHECK.

**فجوة:** لا يوجد trigger على UPDATE/DELETE في `wallet_transactions`، ولا تحقق تسوية بين الرصيد ومجموع الدفتر.

## 6) المهام المجدولة (pg_cron)

وظيفتان فقط: `expire-vendor-grace` و`release-vendor-earnings` (يومياً 03:40).

`ARCHITECTURE §8` يذكر: انتهاء الإعلانات/الفعاليات (كل ساعة)، تقييم مستويات البائعين، فحص الغرامات (أسبوعياً)، تنظيف السلات، إعادة بناء sitemap. **كلها غير مجدولة.** `fn_auto_levels()` موجودة لكن بلا cron.

## 7) التخزين (Storage)

| Bucket | عام؟ | الحد |
|---|---|---|
| `media` | نعم | 50MB |
| `documents` | لا | 50MB |

سياسات `storage.objects`:
- `media_public_read` — قراءة عامة على bucket `media`.
- `media_owner_insert/update/delete` — تتطلب `foldername[1]='u' AND foldername[2]=auth.uid()`.
- `documents_owner_read` + `documents_admin_read`.

`admin-update-bucket` (Edge، يدوي النشر): يتحقق من JWT ثم `profiles.role='admin'`، ثم يطبق حدوداً على الـ bucket بـ service key ويراجع بالقراءة.

**عيب:** `apply` يضع **حد حجم واحد لكلا الـ bucketين** = أقصى الأنواع المفعّلة.

## 9) عزل البائعين — انحراف جوهري

`ARCHITECTURE §4` يحدد العزل عبر:
```sql
vendor_id IN (SELECT vendor_id FROM store_members WHERE user_id = auth.uid())
```

الكود الفعلي:
```sql
create or replace function public.own_vendor_id() ...
  select id from public.vendors where owner_id = auth.uid();
```

`store_members` موجود ويُكتب فيه عند الـ onboarding، وسياسة `store_members_select_own` تسمح بقراءته — لكن **لا يوجد أي جدول آخر يستعلم عنه**. دعوة عضو فريق للبائع (owner/staff) **لا تمنح أي صلاحية**. الحقل `store_members.role` (owner/staff) بلا أثر.
