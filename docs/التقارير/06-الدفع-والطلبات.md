## 2) الدفع (`checkout.tsx`)

صفحة واحدة بأكورديون: `address → shipping → payment → confirm`. حالة فقط، بلا حفظ.

### قواعد الهوية (AGENT §29)
- **البريد:** للقراءة فقط من `viewer.user.email`. ليس حقلاً.
- **الهاتف الأساسي:** قابل للتعديل، مُهيَّأ مسبقاً.
- **الهاتف الاحتياطي:** **إلزامي** ويجب أن يختلف. يُفحص على السيرفر وفي `fn_create_order` بـ `^\+201(0|1|2|5)[0-9]{8}$`.

### الشحن
رسوم واحدة لكل طلب من `governorates.shipping_fee_piastres` للمحافظة الفعلية. كوبون شحن مجاني يصفّرها.

**رسوم الاستلام (pickup) لا تظهر للعميل إطلاقاً** — هي خصم من محفظة البائع: `Σ qty × area.pickup_fee_piastres`، تُنشر مرة عند `handed_to_carrier`.

### الدفع عند الاستلام (COD)
معطّل إذا:
- أي صنف `shipping_mode = "vendor"` → سبب `cod_vendor_ship`
- `total > settings.checkout.cod_max_total_piastres` (افتراضي 500000 = 5,000 ج.م) → `cod_cap`

يُعاد الحكم داخل `fn_create_order` أيضاً.

### إنشاء الطلب
`fn_create_order({attempt_key, payment_method, coupon_code, address})` — **السلطة الوحيدة**؛ العميل لا يرسل سعراً.

`attempt_key = crypto.randomUUID()` لكل تحميل صفحة → idempotency.

أسباب الرفض المُترجمة: `items_unavailable`, `insufficient_stock`, `address_incomplete`, `area_unavailable`, `coupon_*`, `cod_*`, `duplicate`, `payment_unavailable`.

### داخل `fn_create_order` (النسخة الأخيرة: `20261102000002_phase085_commissions.sql`)
1. `FOR UPDATE` على السلة والمتغيرات.
2. التحقق من `vendor_can_sell`، رفض الفعالية، سعر null.
3. السعر لكل سطر = سعر الخصم (min) ثم نسبة الفعالية مع `max_discount`.
4. فحص المخزون.
5. الكوبون عبر `fn_apply_coupon`.
6. توزيع خصم المنتج pro-rata (الباقي على آخر سطر مؤهل).
7. توزيع خصم العمولة: `trunc(coupon% × line commission)`، مع `pairs_with` للكوبون المكدّس.
8. `total = subtotal − discount − cd_discount + shipping`.
9. قواعد COD.
10. `order_sequences` (سنوي) → `ETS-YY-###`.
11. إدراج orders/groups/items، إنقاص المخزون، `coupon_redemptions`، حذف السلة، `order_status_history`.
12. أي استثناء → rollback كامل.

## 3) Kashier

### إنشاء الدفع
أُنشئ الطلب أولاً، ثم:
```
GET {baseUrl}/?merchantId&orderId&amount&currency=EGP&mode&display&redirectUrl&hash
hash = base64(HMAC-SHA256("orderId;amount;currency"))
```
`amount = (piastres/100).toFixed(2)`. `redirectUrl` لا يُوثق به للحالة إطلاقاً.

### الـ webhook (`api/webhooks/kashier.ts`)
- نص خام من `request.text()`.
- `x-kashier-signature` مقابل `base64(HMAC-SHA256("amount;currency;merchantId;orderId;status;transactionId"))`.
- `timingSafeEqual`.
- توقيع خاطئ → **400** (قرار مقصود: لا إعادة محاولة).
- خريطة الحالة: `SUCCESS|SUCCESSFUL|CAPTURED` → succeeded؛ `FAILED|DECLINED|CANCELLED` → failed.

### `fn_confirm_payment` (service_role فقط)
- إن وُجد `provider_ref` ناجح سابقاً → `{ok:true, idempotent:true}`.
- عدم تطابق المبلغ → يدرج `payments` بـ `status='failed'` ويرجع `amount_mismatch`.
- نجاح → `payment_status='paid'`، الحالة `on_hold` إن وُجدت مجموعة `pending_admin` وإلا `processing`.

**ثغرات:**
- لا يعيد فحص `payment_method='kashier'` ولا `status <> 'cancelled'`.
- webhook فاشل ثم ناجح بنفس `provider_ref` يصطدم بقيد الـ UNIQUE → 500.

## 4) COD والاستلام

- الطلب: `processing` + `payment_status='cod_pending'`، المجموعات `preparing`.
- `fn_set_cod_collected(p_order_id)` — أدمن فقط داخل الدالة؛ يرفض `not_cod`/`already_collected`؛ يضبط `cod_collected` + history.
- لا بريد ولا إشعار عند التحصيل. لا جدول تسوية نقدية — المال يُسوّى يدوياً.

## 5) حالة الطلب والمجموعات

```
orders.status:     pending_payment | processing | on_hold | completed | cancelled
payment_status:    unpaid | paid | cod_pending | cod_collected
group.status:      pending | preparing | on_hold | handed_to_carrier
                   | out_for_delivery | delivered | cancelled
vendor_ship_status: not_required | pending_admin | approved | rejected
```

`fn_update_group_status`:
- أدمن: أي حالة مسموحة.
- بائع: `preparing` فقط (النسخة الأولى)، أو عبر `fn_vendor_set_fulfillment` (phase06) الذي **يتوقف عند `out_for_delivery`** — البائع لا يستطيع تعليم `delivered`؛ الأدمن فقط.
- عند `delivered` → `fn_post_earnings`.
- عند `handed_to_carrier` → `fn_post_pickup_fee`.
- عند اكتمال كل المجموعات → الطلب `completed` + `delivered_at`.

## 9) العيب #3 بالتفصيل — لأنه خطأ مالي

```sql
-- 20261102000002_phase085_commissions.sql:271-273
v_unit := v_unit - trunc(v_unit * v_event_percent / 100);
if v_event_cap is not null and v_unit < v_event_cap then
  v_unit := v_event_cap;        -- ← يرفع السعر إلى السقف
end if;
```

المقصود: «لا ينزل الخصم عن سقف معين» — أي يجب أن يكون:
```sql
if v_event_cap is not null and v_discount > v_event_cap then
  v_discount := v_event_cap;   -- تقييد الخصم
end if;
```

**الأثر:** منتج بخصم فعالية 50% وسقف 5000 قرش وسعر 6000 قرش → السعر النهائي يجب أن يكون 3000 (خصم 3000 < 5000). الكود الحالي يرفعه إلى 5000. المنتج يبيع بأغلى من السعر المخفّض المعلن.

نفس الخطأ مُكرَّر حرفياً في `app/features/checkout/pricing.server.ts:152-153` — فلا يظهر للعميل، لكن الكود المالي مخطئ في المكانين.

## 10) ما يعمل بجدية

- `fn_create_order` ذرّية كاملة مع قفل صفوف ومنع تكرار.
- توقيع webhook بـ `timingSafeEqual` + idempotency + فحص مبلغ.
- عزل مستندات البائع عبر `fn_vendor_order_snapshot` (أعمدة آمنة فقط).
- عدد الشحنة الواحد `ETS-YY-###` من `order_sequences` مع سنوي.
- قواعد COD مطبّقة في الطبقتين (UI + RPC).
- `orders_total_consistent` قيد في قاعدة البيانات، لا مجرد تحقق في الكود.
